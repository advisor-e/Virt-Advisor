How firms are using the app

Which firms are actually using the product, and which have gone quiet. This replaces the Team Progress tab at mentor level — that tab lists a firm's advisers by name, which is a firm manager's view of their own people and must not cross the firm boundary. The same underlying activity, counted one level up and stripped of who did it, answers the question a mentor actually has: where is the product landing, and where is it not?

Note the third row: 6 weeks ago still reads Active. That is the 60-day line Mike ruled, shown deliberately rather than described. A firm gets two months of quiet before it is flagged, so a badge on this page means something worth acting on rather than "worth a look".
The last row only exists because the firms list is read — and that has consequences. Activity is recorded in the session tables, which only ever hold rows for firms that have done something. A firm that has never opened the product leaves no trace there, so it can only appear because this page also reads the list of firms itself. That read is the first time anything in our backend queries the firms table, and it must exclude the reserved __platform__ row seeded for mentor storage — which is not a firm. The same read gives us the firm names; where a name is missing the row falls back to its id, so the page degrades to today's information rather than to an error. Inside the Advisor-e master app that table may be theirs rather than ours, which is exactly why the fallback exists.

4 · The other tab, for completeness

Not part of this screen, but part of the same change, and recorded here so the artefact matches what gets built.

Team Case Studies disappears from the Mentor Hub. It is the firm manager's view of their own advisers' shared cases, and shows nothing at mentor level. The mentor already has the correct version beside it — the Case Reviews tab, which shows only cases a firm manager has anonymised and explicitly approved for sharing. Rolling the firm tab up instead would have walked straight past that consent gate, so it is hidden, not widened.

5 · What will not have been proven when this ships

Stated before building rather than discovered after.

No MySQL exists on this machine, so none of this will have been seen working against real data. It will be proven by tests and by the development fallback — which is a different claim, and a weaker one. The repo has been caught by exactly this before: Advisory Distinctions authoring and Template Check rulings were both built, tested and signed off while being incapable of writing to a real database, because the dev fallback absorbed the failure silently. The firms-table read here is new ground for this codebase and is the part most likely to behave differently in production.

6 · BUILT 2026-08-09 — and every difference from this page

The rule is to open the artefact, put it beside the build, and name every difference. Three, all deliberate, none of them a change to what was ruled. A deviation that is named is fine; one that is not is how a screen quietly stops being the screen that was approved.

Differences

  1. No page heading in the build. This page carries an <h1> reading "How firms are using the app". In the Hub that wording is the tab label, so an <h1> inside the tab body would print the same words twice, one line apart. The lede beneath it is unchanged.
  2. The columns are sortable. This page shows a static table; the build lets the mentor sort by any column. An addition, not a change — the default order is still busiest first.
  3. The firm id line appears only under a real name. This page shows the id beneath every firm, including the never-started row. In the build, a firm the directory could not name has its id AS its name, so printing it twice would suggest we know more than we do. The row carries a flag saying which of the two it is.
