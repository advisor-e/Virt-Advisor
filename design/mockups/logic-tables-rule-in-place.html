3 · A ruling and an edit must not look like the same act

This is the one real risk in putting the two together, and it is a design question, not a coding one. On this page a text change waits for Save. A ruling does not — it is recorded the moment it is pressed, exactly as it is on the Template Check screen today.

Proposed: the strip states its own saving, separately from the table's ?

Decision Workpaper You ruled → points at FM Board White Paper ✓ Recorded ?
Saves the branch wording above. Rulings are already recorded ? — they are not waiting for this button.
Why this is stated so plainly. On 2026-08-12 the editor's THEN column was found reading one field and writing another, so a reworded recommendation could be saved as an action and travel past the safety gate — no error, no failing test. Two write paths that look alike on one row is the same shape of risk. If the two savings cannot be told apart at a glance, the merge is not worth doing.
A ruling never edits the table. It records your decision about a name. Changing the sentence to use the published title is a separate, reviewed step — the existing "Accept and push" queue on the Template Check screen — and it is unchanged by this.

Why this is not much code. Every finding is already filed under table + branch — live example from the running server: quickfire::qf_branch1c_salvageable::covid agenda programme — and the Logic Tables editor already keeps each branch's own id when it loads a table. The two already have the key they need to be joined; this is display, not new plumbing.

Not proposed here, deliberately: merging the two tabs into one, or removing the Template Check tab. The list is where you see what is left across all 30 tables; the table is where a single name is best judged. Losing the first to gain the second would trade one kind of flicking for another.
