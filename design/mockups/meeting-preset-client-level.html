Five things this screen does, and why each is here rather than invented.
  • A fourth source appears — For this client — and it names who set it. D2 makes a client's list shared between the advisor and the firm manager, so unlike Added by you a client-level point may have been written by somebody else. The advisor-level ruling of 2026-09-08 (question 2: name them, do not count them) is applied here for the same reason: a name says who to ask. Question 4.
  • The verbs change one word. Not for my meetings becomes Not with this client; Add a point of my own becomes Add a point for this client. The blast radius is in the label, as the advisor level's off for you only is.
  • The layers stack: firm → your own level → this client. A point you set aside for all your meetings stays aside here, and a point set aside for this client is off for this client only, for whoever runs the meeting. Question 2 asks whether the client layer may reverse your own set-aside; the drawing says no.
  • A switched-off point is shown, not hidden, for the reason written on the manager's screen and repeated at the advisor level.
  • Only a client-level point can be edited or removed here. The firm's and Advisor-e's words are never edited below their level; the advisor's own points are edited on the advisor's own list, not from inside a client's.

Where it is stored, and how it reaches the report

Follows §5 and the advisor level as built — no decision needed, stated so it is checkable
  • Two keys per client on the firm's own row, mirroring the advisor level exactly: meeting-observation-entity-declines:<clientId> and meeting-observation-entity-own:<clientId>. One row per client, one writer at a time per key, so the lost-write fault item 4.75 closed cannot return. No schema change.
  • Every entry is stamped with who wrote it — name and whether they wrote it as an advisor or a firm manager — from the verified token at write time, because this app holds no advisors table to join a name out of later. Same pattern as the advisor level.
  • The client id is checked against the firm's register on every write, as the recorder already does (clientStore.getById(id, req.firmId)). A client of another firm is a 404, never a write.
  • The report applies the same layer through the same function. presetFor in meetingReview.js already reads the meeting's client; it applies the client layer after the advisor layer, through one shared function the screen also calls — the fault found on 2026-09-08, where the screen and the report disagreed, must not be re-made.
  • Deleting a client from the register leaves its two keys in place, readable in history, unreachable from any screen. Nothing is silently lost; nothing dangles on a picker.

Five questions

All five ruled 2026-09-10 · the fifth removed Stage C
Question 1 — ✅ RULED BY MIKE, 2026-09-10: ONE SHARED LIST PER CLIENT. "a firms internal proceedings will determine who meets with them but at least everyone is on the same page"

Is a client's list one list, shared by everyone who meets them — or one per advisor per client?

D2 says the advisor and the firm manager may each set a client's points. That can mean one shared list they both write to, or a manager's client list and each advisor's private client list resolved one after the other.

Recommendation: ONE list per client, shared. Mike's own reason for D2 — a partner preparing a difficult client's meeting for a junior — only works if the junior sees what the partner set. A private list per advisor per client would make the partner's preparation invisible to the person it was for. It is also what "the level ends at the business entity" means: the entity is the level, not the pairing.
Against: two advisors who both meet the same client can undo each other's set-asides, and the screen will show it rather than prevent it. The name beside each decision (question 4) is what makes that a conversation instead of a mystery.
Question 2 — ✅ RULED BY MIKE, 2026-09-10: NO. "the person responsible for completing that task should be the one to take it off"

Can a client-level entry put back a point the advisor set aside for all their meetings?

Recommendation: NO. The layers apply firm → advisor's own → client, and the client layer only sets aside or adds. An advisor who has said not for my meetings should not find the point back on their list because a colleague set something for a client. If they want it with this client, they put it back at their own level.
Against: a manager preparing a junior's difficult meeting may want a point the junior habitually skips to be checked this once, and this says they cannot force it. That is P14's downward-only rule reaching the bottom of the cascade, and it is the same answer the advisor-level Stage C gave: a mirror, not a control.
Question 3 — ✅ RULED BY MIKE, 2026-09-10: YES, any advisor in the firm, named on every entry

Who may set a client's points — any advisor in the firm, or only the advisor who meets them?

Recommendation: ANY advisor in the firm. The register is firm-wide and the app holds no record of which advisor "owns" a client — the meeting record names the advisor who recorded, which is after the fact. A rule this app cannot check is a rule it would fake.
Against: an advisor can set points for a client they have never met. With the name beside every entry that is visible, and a firm that wants it stopped has a manager who can remove it.
Question 4 — ✅ RULED BY MIKE, 2026-09-10: YES, always

Does every client-level entry name who set it?

Recommendation: YES, always — added by Tom Boyd, set aside by Ruth Kelleher. The advisor level shows Added by you because only you can write there. A shared list needs the name or an advisor asking "who took that off?" has no answer, which is the exact failure D1 was ruled to prevent.
Against: it is a small record of who did what to a client's list. It is configuration, not anything from a meeting, so P13 is not engaged, and the advisor level already names advisors to their manager for the same reason.
Question 5 — 🔴 RULED BY MIKE, 2026-09-10: NO MANAGER SCREEN AT ALL. "WHY does the firm manager need a copy? ... it's the PARTNER or firm manager that owns the client data base - NOT the advisor. WHY are we building two levels of this??" Stage C deleted from this page.

Is the manager's half a section on the existing Meeting Review tab, firm tier only?

Recommendation: YES. The client register belongs to the firm, so the two middle tiers and the mentor have no clients to pick from — a client picker at the mentor tier would be an empty list, and an empty screen reads as a broken one. Same tab, because a manager deciding what is checked with a client is deciding the same thing they decide for the firm, one client at a time.
Against: the Meeting Review tab is already long. A second tab would be cleaner and would cost a fifth entry in the hub menu for one section.

Not drawn, and why. The report's header line naming the client's points is not drawn: presetFor already applies the pre-set to the report through one function, and the client layer joins it the same way, so there is nothing new to see there. The business-entity level of the meeting types (which kinds of meeting exist for one client) is not drawn either — D4 switched types off per tier, and nothing in Mike's rulings asks for a type per client.
