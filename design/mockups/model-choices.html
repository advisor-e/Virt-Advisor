Model Choices

Nineteen calculation models are described to the AI on every client conversation. It names one when it judges one fits. Until now, nothing anywhere wrote down which one it named, or what it was asked — so the only way to check its judgement was for somebody to sit and read conversations.

Drawn below as the mentor's view, which reads every firm. A firm manager opens the same tab and sees their own firm alone; a group manager their group. That is the roll-up every other report on this hub already does.

What is built, and what is not

NOTHING ON THIS PAGE IS BUILT. This is a drawing. Every figure in it is invented to show the shape of the screen — not one of them is a reading from the app.

What IS already true, and is what makes this cheap: the instruction the AI is given already says "give its exact page path from this list so the advisor can open it". Those paths — /debtor-drag, /three-way-forecast — are unique strings that come from data/report-model-summaries.json itself. So finding a model mention in a reply is an exact match against a known list of nineteen, not a guess. No heuristic, and nothing new to teach the AI.

⬥ Decision 1 — how we know a model was named

RULED BY MIKE 2026-09-16 — as recommended, both

His words: "yes to both". The AI declares its model choice with a marker, AND the page-path scan is kept underneath it as the fallback, and each row records which of the two produced it.

🔴 The ruling paid for itself the same day — and exposed a second fault

BUILT 2026-09-16, THEN RUN AGAINST THE LIVE AI. Six discover-mode conversations. The marker was written 0 times in 3 with its instruction sitting in data/report-model-summaries.json, and 1 time in 6 after it was moved into the system prompts (client.txt SECTION 12, discover.txt) beside the template marker that has worked since item 4.53.

The fallback is the only reason any of it was recorded. Three of the four rows came from the page-path scan. Had this been built on the declaration alone — the tidier design — the screen would have been very nearly empty and nothing would have said why.

🔴 WHAT IS STILL WRONG, AND IT IS FILED AS ITEM 7.6 rather than left here. A model that is NAMED is caught exactly, every time, because its page path is a unique string. A decline has no second source, so the declines band below under-counts, and nothing on the screen says so. The one time the marker did fire was a decline that had recorded nothing at all before the move, so the change was worth making — it is just not finished. ⚠ The client-mode Phase 3 path is UNTESTED: SECTION 11's template marker works reliably there, and SECTION 12 sits beside it, so it may already be fine. That is 7.6's first step.

The recommendation, kept — the AI declares it, and the page-path scan stays as the fallback

Add a machine-readable marker the AI writes at the end of its reply, exactly as it already does for templates, and keep the page-path scan underneath it. Record which of the two produced each row — that is the Page path in prose tag on the screen above.

Why not the scan alone. The scan is exact for a model that was named — the nineteen page paths are unique strings. But it can never see a decline. "The app has no model for this situation" is ordinary prose with no fixed wording, and matching it by phrase is the kind of guesswork that puts wrong rows on a screen people then trust. A declared marker is the only honest way to record the third box on the screen above — and that box is the AI getting it right, which today is exactly as invisible as the failures.

Why the fallback stays. Item 4.53 established this for template recommendations, and its reason applies here word for word: the AI obeys the declaration instruction only sometimes. Keeping the scan means a mention is still caught when the marker is missing, and recording which one fired means a drift in obedience shows on the screen instead of quietly shrinking the numbers.

What it costs. One line added to the instruction block in data/report-model-summaries.json — the file whose instruction you changed on 15 September — and a strip step so the marker never reaches the advisor, which the engine already does for the template marker on all three response paths.

⬥ Decision 2 — what is stored beside the model name

RULED BY MIKE 2026-09-16 — WIDENED. The recommendation below was too narrow.

A row holds: when · firm · advisor · advisory domain · the model named (or that it declined) · how we knew. Still never the advisor's own words. The page is scoped by tier — a firm manager sees their own firm, a group manager their group, the mentor every firm.

His question is what found the fault, and it is worth keeping in his own words: "if im a manager, group manager or global manager and I don't see the advisors words - will i have enough context to be able to use the findings to make changes? - how will it help me build a better coaching environent?"

The recommendation had bundled two different things together and called them both privacy. They are not the same. The advisor's own words describing a client's business genuinely are the line — lifting those onto a screen read across firms is a real privacy step. The firm and the advisor are not a new step at all: advisor_va_sessions already records advisorId, advisorName and firmId on every completed session, and firm managers already read their own team's activity on Team Progress. Leaving them off kept the page tidy and cost it the thing he asked about — a firm manager would have opened it and found nothing of their own in it.

It also restores his own ruling of 2026-08-10, that every report rolls up. With the rows scoped by tier there is no exception left to argue for.

What does NOT change: the advisor's description of their client stays inside their firm, on their own saved case, where the decision trace already keeps it. And retention is still settled without a dial — see the last paragraph below, which the ruling does not disturb: a firm id and an advisor name are already held on the session row beside it and on the same footing.

The recommendation, kept — it was too narrow, and this is why

A row holds: when, the advisory domain, the model named (or that it declined), and how we knew. No firm, no advisor, no client, and not a word of what was typed.

Why this is the important one. This page reads across every firm on the platform — that is what makes the pattern visible, and it is the same reason the Logic-Lab Report can only exist at the mentor tier. The decision trace already stores the advisor's own intake answers, but that stays inside the firm, on their own saved case. Carrying those words up to a platform-wide screen would move one firm's client situations in front of Advisor-e staff, and that is a privacy decision, not a reporting feature.

It costs nothing you need. The domain is the situation, for this purpose: a governance conversation offered a cash forecast is the whole fault of 15 September, and the row above shows it with no client content at all. Where somebody does need the detail, the conversation is findable inside the firm that had it, by the people entitled to read it.

And it settles retention without a dial. A row holding a timestamp, a domain name and one of nineteen model names is not personal data and describes no business. There is nothing here that has to be deleted on a clock, so no retention control is proposed — unlike the staff register, where the opposite was true.

The recommendation, kept — the name survived it; the group and the tiers did not

Model Choices, in the "Your AI coach" group, mentor tier alone.

Two words, plain, and it says what the page holds: the choices the AI made. Appended to the end of the group, which moves nothing already on a manager's screen.

Why not "Model Mentions" or "Model Accuracy". Mentions describes the mechanism rather than the thing — you would be reading a page named after how it was built. Accuracy claims the page judges the AI, and it does not: it reports, and you judge.

Mentor tier alone, and here is the judgement rather than an assumption. The rule's default since 2026-08-24 is the mentor's view only, and it is right here for a reason that is easy to state: the content this page audits is platform content that no other tier may edit. The model summaries describe what the maths does; nobody at a firm, group or global tier gets to change when Lease vs Buy is the right tool. A screen shown to a tier that cannot act on it is a screen that trains people to ignore a tab. If that ever changes — if a firm is ever allowed to say when its advisors should reach for a model — this page cascades on the same day, and so does the editing screen the standing rule would then require.

What can be built now, and what cannot

⚠ Two differences between this drawing and the backend that was built — named here rather than found later

1 · The period selector is drawn and is not built. GET /api/model-choices returns the most recent 2,000 rows for the caller's scope and takes no date range. Building the screen means either adding one to the route or filtering in the component; the drawing is what was approved, so the route is what has to catch up, and this line exists so that is a decision rather than a surprise.

2 · The first band's largest number is not available yet. "142 conversations where a model could have been named" is a count of client conversations, which lives in advisor_va_sessions — a different table. The route returns named, declined and viaProse; the fourth figure needs that second read. Everything else on the page is served.

The screen half is blocked on this machine — stated before any code, not discovered after

The recording half is free, and is BUILT (2026-09-16). server/utils/modelChoiceScan.js, the marker in the two prompt files, the strip on all three response paths, the streaming hold-back, advisor_model_choices with its dev-file fallback, logModelChoice, and GET /api/model-choices — none of it touches another machine's work.

The tab is not. Putting a tab on the hub means editing components/FirmManagerHub.vue in three places — TAB_TIERS (all four tiers, per Decision 3), NAV_GROUPS (the end of "Rolled up from below") and the panel itself. That file is named in item 9.1's touches, and 9.1 has been active on the desktop since 10 September. It is the same wall 5.1's retention dial hit on 15 September.

Which is why this drawing exists now rather than later. With the screen settled, the recording half can be built knowing exactly what it has to feed, and the tab becomes a small, well-specified job on the day the desktop releases the hub file.
