7 · The six rulings — all given by Mike, 2026-09-08
  • 1 · Two documents give the same asset class a different rate. ✅ The newer publication date wins, and the older figure is shown beside it — never silently dropped, so the firm sees the disagreement and can overrule it. Silent selection is how a wrong rate becomes invisible.
  • 2 · A firm has loaded nothing. ✅ It inherits the nearest approved table above it in the cascade — group manager, then global group manager, then mentor — read-only and badged with which tier it came from. The app's own defaults apply only when no tier above has one.
  • 3 · A client's country has no table. ✅ Carry on with today's defaults, badged app default on the forecast itself. Never block the advisor. Stopping someone mid-report because a manager has not loaded a document punishes the wrong person.
  • 4 · Scope of an approved table. ✅ It is tagged with its country and applies only to clients in that country. A New Zealand rate would otherwise quietly depreciate an Australian client's assets.
  • 5 · Who may load, and who may approve. ✅ An advisor may LOAD a document; only the firm manager APPROVES it. Approving a rate table changes every forecast the firm produces, and approval stays on the role gate the hub's other editable blocks already use.

⚠ QUESTION 4 GREW A SIXTH, AND IT CHANGED THE ANSWER TO QUESTION 5. Mike asked: "does the advisor have the ability to enter a tax doc for the client with the different country?" As first drawn the answer was no — the firm manager was the only one who could load anything, so an advisor with a client in an uncovered country got the built-in defaults and no way to improve them without waiting on their manager. That is the wrong answer for the person sitting in front of the client.

Letting an advisor load and approve would have brought back the problem that argued against firm-level ownership in the first place: several advisors in one firm each extracting the same country's rates, ending with different tables, and a lender-facing forecast built on whichever one that advisor happened to make — no second pair of eyes on a number a bank reads. Splitting loading from approving answers both.

Security, stated before any code is written — CLAUDE.md requires flagging this. An upload is an attack surface. The build follows the repository's own procedure (.claude/skills/master-export-upload), adapted where it assumes JSON:

  • Identity from the verified token only. The firm comes from firmAuth, never from the browser — the existing rule against cross-firm access.
  • Size cap and type check before the body is read, then parse inside try/catch. A PDF, not JSON, so the shape check is on the extracted table instead: every rate must be a number in a plausible range and carry a source, or the row is refused.
  • The live table is never overwritten in place. The previous approved version is kept as last-known-good, so a bad upload cannot leave a firm with no rates.
  • The storage path is derived from the verified firm id, never from the file's own name — no path traversal.
  • The document goes to the AI; nothing about a client does. Tax PDFs are public, so no personal-data question arises and no exception to CLAUDE.md's stripping rule is needed.
