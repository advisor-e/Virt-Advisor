The questions as they were put — kept beside the rulings

1 · The proposal sentence, as drawn on Screen A?

"From what you've said, the main issue looks like {issue} — {reason}. Have I got that right, or is it really something else?"

Recommended: yes, as drawn. It is the same shape as the area check-in the advisor has just answered, so the second question reads as a continuation, not a new form; the issue name is in bold so the eye lands on it; the reason is the advisor's own words reflected back, which is the cause-first rule of June applied again. Against: "main issue" is a looser phrase than Mike's own "primary issue" — but "primary issue" is a term of the design, and on a screen it reads as jargon to an advisor mid-conversation.

2 · The "Main issue" trace row, as drawn on Screen D?

Label "Main issue"; value "{issue} · confirmed by you" / "· reframed by you" / "none proposed — nothing in what you said matched a known issue".

Recommended: yes, as drawn. It matches the voice of the row above it ("Area I focused on"), says in two words whether the advisor accepted or rewrote it, and the nothing-matched line says why there is no name rather than leaving a blank. Against: the nothing-matched line is the longest value on the panel; a shorter "none proposed" would fit the row but would not tell the advisor it was their words, not the engine, that produced no match.

3 · Should the confirmed issue also be shown on the case-review screen's summary?

The trace on Screen D carries it, and the firm manager sees that same trace on a saved case. The question is whether the issue name is also printed up front on the case-review summary.

Recommended: no, not in this release. The trace carries it, the pool reads it from the trace, and adding it to the summary is a second screen for a field that has not yet been seen working in a live session. Against: an advisor reviewing the case weeks later would like the issue up front without opening "Why this recommendation" — a fair point, and one to raise as its own request once the field has been live for a while.

What this drawing does not decide How the engine ranks the issues against the cause words, when it asks the model to break a tie, and the exact shape of the stored trace key are the plan's, pinned by tests, not by this drawing. The three sister drawings (the Outcome Learning page, the trace line for a lift, the Template Profiles tab) are their own questions.
Which tiers get this, and why

The advisor, in their own conversation and on their own trace — the proposal is a turn in the intake, and the Main issue row is on their "Why this recommendation" panel. The firm manager sees the same trace on a saved case in the hub (FirmManagerHub.vue renders the same panel through the same mixin), so the new row appears there with no second build. No tier above the firm sees an individual advisor's conversation or trace today, and this changes nothing about that. The issue names themselves are Mike's authored list and are not edited on any screen by this change.
