## Design Decisions — Locked

### Decision 1: Naming Convention
Solution categories are named as **interventions** — verb + noun phrase.

| Avoid | Use |
|---|---|
| "customer acquisition gap" (problem name) | "Build customer acquisition system" |
| "more customers" (outcome) | "Map customer purchase process" |
| "Customer Journey" (template name) | "Diagnose sales conversion leaks" |

**Naming test:** If I gave this category to an advisor, would they understand what work they are about to perform?

Approved verbs: Build · Design · Diagnose · Map · Create · Develop · Implement · Assess · Plan · Facilitate · Model · Analyse

**Granularity rule:**
- Too broad: "Fix sales"
- Right: "Build sales process"
- Too narrow (template name): "Create sales call script"

Each solution category should contain 3–10 templates. No category with >15 templates — too broad.

---

### Decision 2: Domain Scoping (Opinion 2 — confirmed)
Solution categories are **domain-scoped by default**. Cross-domain categories are not permitted unless templates are genuinely identical across domains.

**Correct:**
```
sales_performance_coaching  →  domain: sales_marketing
management_performance_coaching  →  domain: staff
```

**Incorrect:**
```
performance_coaching  →  domain: [any]  // DANGER — resolver cannot distinguish
```

**Exception rule:** If a category is genuinely domain-agnostic (e.g. "Build financial model" applies equally to Profitability, Valuation, Financial Management with the same templates), it may span domains — but must have explicit domain mapping in the schema:

```json
{
  "category": "build_financial_model",
  "applicableDomains": ["profitability", "valuation", "financial_management"],
  "templatesByDomain": {
    "profitability": ["template-a", "template-b"],
    "valuation": ["template-c"],
    "financial_management": ["template-a", "template-d"]
  }
}
```

---

### Decision 3: Sequence
1. Define all solution categories first (domain expert vocabulary session)
2. Validate against 10 representative templates
3. Refine categories based on gaps
4. Classify all 131 templates

**Never classify templates while category design is still moving.**

---

### Decision 4: Template Classification Approach
- Classify **41 templates with content summaries** first
- **90 templates without content summaries** — defer classification. Write a 2–3 sentence purpose statement for each before classifying. Do not guess.
- Classification is manual domain expert work — not generated by scripts or keyword matching

**Classification interface per template:**
```
Template ID: [page ID]
Title: [name]
Purpose: [from search content]
Section / SubSection: [from search content]
Current Tags: [from search content]

Domain expert assigns:
- Primary Domain:
- Primary Issue (from normalized map):
- Solution Categories (1–3):
- Complexity Level (1–5):
```

### Decision 5: Validation Before Full Classification
Paper test with 8–10 complete advisory scenarios before classifying all 131 templates.

**Validation checklist:**
- Every primary issue maps to ≥1 solution category ✓
- Different primary issues map to different category sets ✓
- Each solution category has ≥3 candidate templates ✓
- No template left unclassifiable ✓
- No solution category contains >15 templates ✓

## Key Insight — The 13-Question Framework

The universal question framework already handles cross-domain disambiguation that might otherwise require complex routing rules.

**The 13 standard questions (every conversation):**

| # | Field | Phase | Always/Conditional |
|---|---|---|---|
| 1 | (opening) | Detection | Always |
| 2 | clientRaisedIssue | Situation | Always |
| 3 | situationDiagnostic | Situation | Always |
| 4 | disambiguationAnswer | Situation | Only on domain tie |
| — | industry | Universal | Always |
| 5 | ownership | Client Acumen | Always |
| 6 | growthStage | Client Acumen | Skip if NFP/public |
| 7 | advisoryStaircase | Relationship | Always |
| 9 | advisorExperience | Advisor | Skip if profile exists |
| 10 | advisorConfidence | Advisor | Always |
| 11 | advisorEnjoyment | Advisor | Skip if profile exists |
| 12 | advisorMeetingCount | Advisor | Always |
| 13 | advisorSessionLength | Advisor | Always |

**Q3 (situationDiagnostic)** is particularly important: "What contributed to this situation, and are there any downstream effects?" — the advisor's answer naturally distinguishes external causes (market/economic) from internal causes (process/product/competitive), resolving cross-domain ambiguities without hardcoded rules.

**Implication for CaseState:** These 13 answers must feed CaseState properly. The routing follows from what the advisor said — not from code rules.

## External Review Findings — Summary

Both panels (3 senior engineers each, 2 rounds of review) confirmed:

1. The Primary Issue Map is the most important design work in the engagement
2. Solution Categories are the correct bridge — not signal-to-template mapping
3. Domain-scoped categories prevent routing errors (Opinion 2 chosen over Opinion 1)
4. Workshop 2 is ontology design, not template classification
5. The intervention vocabulary is the asset — scoring engine and resolver are implementation details on top
6. Category explosion (60–90 categories) is the most dangerous failure mode — avoid by targeting 15–25 total
7. The 90 empty templates must not be classified without content
