# Quizzes — the Brief

> **Read this before touching quiz content, the firm quiz builder, or how a session is
> graded.** Current rules only. The history is in [`quizzes-history.md`](quizzes-history.md).
>
> **Covers:** the capability questions — where they come from, who may edit them, and how they
> reach a course session. **Does not cover:** how a session is delivered
> ([`course-builder.md`](course-builder.md)) or what happens to the score
> ([`advisor-progression.md`](advisor-progression.md)).

---

## 1. Design philosophy

**A quiz is a firm's teaching material, not the platform's.**

The platform provides a strong base set, and a firm can edit it and add its own — so a firm can
build quizzes that support how *they* teach rather than only what we shipped. Same promise as
the rest of the hub: plain-English editing, no developer, and nothing lost if they change their
mind.

**Nothing is free-standing.** Every quiz topic is bound to a **real template that exists in that
firm's content** — a platform template, one cloned down from a group or brand, or the firm's own.
A quiz is always *about* something the advisor can actually go and look at. A topic floating free
of a template is a question with no lesson behind it.

**The questions are somebody's intellectual property**, transcribed from source material, and
they are treated that way: a topic heading that cannot be bound to exactly one template is
surfaced for a human decision, never guessed.

---

## 2. Key principles — the non-negotiables

**P1 · A quiz topic is bound to a template that already exists.** The quiz builder authors
questions *against* templates; it never creates one. Template creation lives in Advisor-e.

**P2 · The master content export is read-only here.** It is the north star and is never modified
from this app.

**P3 · A level never edits the base — it overrides.** The platform set stays untouched, which is
what makes "reset to the platform version" possible at all.

**P4 · Quizzes cascade by row decision**, like Advisory Distinctions: switch a row off, edit it,
reset it, or add your own, resolved against the level above. Untouched rows keep receiving
improvements from above; edited rows are protected.

**P5 · Own-row id prefixes stay distinct per tier** — mentor `mq-`, global `xq-`, group `gq-`,
firm `fq-`. Two tiers sharing a prefix put two different rows under one identity.

**P6 · A grading failure records "ungraded", never an invented score**, and ungraded answers are
excluded from averages and certificates.

**P7 · Overrides ride the shared store**, so version history and restore come free and the
authorisation guard is the one already in use.

**P8 · Transcription is signed off before it ships.** The question and answer text is the
owner's material; it is confirmed, not assumed.

## 3. Design considerations

**Two ways a question can reach an advisor**, and they behave differently: generated by the AI
from the session content, or taken from a fixed authored bank. The authored bank wins where one
exists.

**A fixed bank must be keyed on something stable.** Keying overrides on AI-written session titles
meant they silently never fired — the titles change between generations. Never key content on a
value a model wrote.

**The grader must see what was taught.** It gets the same capped session summary the
question-writer received, so answers are marked against the course content rather than the
model's general knowledge.

**Binding a topic to a template is done by a resolver, not by exact title matching.** The export
carries no stable unique id per template — the `page` value is a deliberately shared page
grouping, not an identifier — so matching is by resolved name, and an ambiguous heading is a
human decision.

**The template picker needs the firm's own content.** A firm authoring a topic must choose from
*their* templates, which means the page needs that firm's export. How that arrives is a known
open dependency, not a solved problem.

## 4. For the coder

### Where things live

| Piece | Path |
|---|---|
| The firm-facing screens | `components/firm/FirmQuizzes.vue`, `components/firm/FirmQuizQuestionForm.vue` |
| Resolution and storage | `server/utils/firmQuizzes.js` |
| Override storage, version history | `server/utils/firmOverlay.js` |
| Template-name resolver | `server/utils/resolveTemplateName.js` |
| Course-side overrides | `server/utils/quizOverrides.js` |
| Scoring | `utils/quizScoring.js` |
| Content | `data/course-quizzes.json`, `data/quizzable-sections.json` |

### The data shape

A **topic** is bound to a template and carries an ordered list of entries; each entry is a
question, an answer and a key point. Topics carry their provenance — which bank they came from —
so a generated question can be traced back to the material it was drawn from.

### What a firm can do

Edit any provided topic's questions, answers and key points; add a topic bound to one of their
templates and author its content; add, edit, reorder and remove entries within a topic; and
restore any earlier version.

### Traps that have actually bitten

1. **An override keyed on an AI-written title never fires** — and nothing reports that it
   didn't.
2. **A grading failure once invented a 75% pass.** Any new failure path produces "ungraded".
3. **A save can be refused by the database while the screen reports success.** Fixed by
   discriminating on the SQL state; a new tier scope still needs its reserved row seeded.
4. **Exact-title tests are brittle.** The locking test proves every topic resolves to exactly one
   template, which is the property that actually matters.

### Known state

MySQL has never been provisioned, so firm quiz edits run on the dev-file fallback — buildable and
demonstrable, but not persisted. The per-firm content export needed by the template picker is a
dependency on the master app, not something this repo can solve.
